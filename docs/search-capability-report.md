# 中文检索能力实测报告

> 任务：证伪「FTS5 默认分词能不能做中文检索」这个假设（设计方案 21.5 / CONTRACTS §7）。
> 方法：全部在本机 `node:sqlite` 上实测，语料为合成数据（广告设计 + 建筑工程资料口味），零生产数据。
> 所有数字可用 §7 的命令重跑复现；原始数据在 `packages/search/experiments/results/`。

---

## 0. 结论

**能用，但不能"FTS5 建个表就上"。**

本机 `node:sqlite` 的 FTS5 编译完整可用，`trigram` tokenizer 也能建成；但默认 `unicode61` 对中文**按词检索是失效的**——它把一整段连续中文（甚至中文 + 相邻数字）当成**一个 token**。直接上默认分词，中文两字词命中率 25%、单字 20%、昵称 0%、口语长查询 0%。

落地方案（已实测）：

| 层 | 用什么 | 实测结果 |
|---|---|---|
| 主路 | FTS5 `unicode61` + **char-space 检索副本**（CJK 逐字加空格、数字↔字母边界切开） | hit@10 **100%**，P@10 **83.6%**，MRR **0.981** |
| 补充 | FTS5 `trigram` + 原文 | hit@10 61.1%（两字以下静默 0 命中，只能当补充） |
| 兜底 | 自维护 n-gram 倒排（覆盖率诊断 + 空结果兜底） | 召回 100%，但 P@10 仅 49.9%，**不进正常排序** |
| 最后兜底 | 参数化 LIKE（只查本包索引副本） | 短查询 88.9%，长口语查询 0% |
| 融合 | RRF（char 1 : trigram 0.6 : ngram 0） | hit@10 **100%**、recall@10 **100%**、P@10 **83.6%** |

对照：纯 FTS5 默认分词 hit@10 只有 **50.0%**，而这个 50% 全部来自 ASCII 类参数，中文类基本全灭（见 §3.6 的分类拆解，不要把它误读成"中文一半可用"）。

## 3. 原始测量数据

### 3.1 FTS5 与 tokenizer 能不能建

实测建表结果（`experiments/probe-tokenizers.mjs`，6 条探针文本）：

| tokenizer 规格 | 建表 | term 数 |
|---|---|---:|
| `unicode61` | ✅ ok | 20 |
| `trigram` | ✅ ok | 151 |
| `porter` | ✅ ok | 20 |
| `ascii` | ✅ ok | 16 |
| `unicode61 remove_diacritics 0` | ✅ ok | 20 |
| `unicode61 remove_diacritics 2` | ✅ ok | 20 |
| `porter unicode61` | ✅ ok | 20 |
| `trigram case_sensitive 1` | ✅ ok | 151 |
| `unicode61 separators ' '` | ✅ ok | 20 |

结论：本机 FTS5 编译完整，**9 种 tokenize 组合全部建表成功**。

### 3.2 各 tokenizer 对中文的真实切分（`fts5vocab` 直读，不是推测）

`unicode61`（默认）对 6 条探针文本切出的全部 term：

```
000 | 03图里首层平面标高是0 | 1200mm | 186c | 2400mm的板材 | 6m | build | cafe
deletion | epoch与pnpm | fts5的trigram分词器对三字以上中文才有效 | pantone | resume
run | web | 喷绘精度1440dpi | 层高3 | 建施
用readsurface读取画布像素前要先等重绘完成 | 色卡
```

看清楚三件事：

1. `用readsurface读取画布像素前要先等重绘完成` —— **一整句中文 + 中间夹的英文词，是一个 token**。
2. `03图里首层平面标高是0` —— **中文和相邻数字粘成一个 token**，所以 `建施-03` 这类编号的 phrase 查询也对不上（库里第二个 token 是 `03图里…`，不是 `03`）。
3. `epoch与pnpm` —— 中英粘连同样整段一个 token。

这就是「默认分词对中文不可用」的**机制**，不是"效果差一点"。

`trigram` 切出 151 个 3 字符窗口，含符号窗口：

```
-03 | .00 | .6m | 03图 | 00，| 0dp | 120 | 144 | 200 | 240 | 3.6 | ... | 施-0 | 用re | ，pa
```

`ascii` tokenizer 对中文**更糟**（不是更宽松）：

```
1200mm×2400mm的板材，喷绘精度1440dpi   ← 一个 token
色卡，pantone                          ← 一个 token
```
`ascii` 只把 ASCII 非字母数字当分隔符，非 ASCII 字节（中文、全角标点）全部保留进 token，且不折叠大小写重音（`café` 仍是 `café`）。**ascii 不能用于中文。**

`porter` 只对 ASCII 词做词干化，中文不受影响：
```
deletion → delet | resume → resum | pantone → panton | 中文 term 与 unicode61 完全一致
```

`remove_diacritics` 对中文无影响（中文没有变音符号），只影响拉丁文本：

| 规格 | `Café` | `résumé` |
|---|---|---|
| `unicode61`（默认 = 1） | `cafe` | `resume` |
| `remove_diacritics 0` | `café` | `résumé` |
| `remove_diacritics 2` | `cafe` | `resume` |

`trigram case_sensitive 1` 保留大小写（`FTS` / `Sur` / `PAN`），默认 trigram 大小写不敏感（`fts` / `sur` / `pan`）。

`unicode61 separators ' '`：**建表通过，但 term 输出与默认完全一致**，实测未观察到任何 token 变化（`×` 仍然分隔、下划线仍然分隔）。本方案不使用该参数——char-space 已经解决需求，不需要自定义分隔符。

### 3.3 MATCH 查询构造：原始输入会直接抛错

把用户输入原样丢给 `MATCH ?`（不是猜测，实测）：

| 查询 | 原样 MATCH 结果 | 转义成 phrase 后 |
|---|---|---|
| `建施-03` | ❌ `no such column: 03` | ✅ ok |
| `JS-2026-017` | ❌ `no such column: 2026` | ✅ ok |
| `1.2m` | ❌ `fts5: syntax error near "."` | ✅ ok |
| `build:web` | ❌ `no such column: build` | ✅ ok |
| `铜版` | ok，命中 0 | ok，命中 0（这条是分词问题，不是语法问题） |

**这条是线上必崩项**：`-`、`:`、`.` 在 FTS5 查询语法里都有含义。必须把每个 token 包进双引号 phrase（内部 `"` 转义成 `""`）。实现见 `buildFtsMatch`。

### 3.4 trigram 的短查询边界：静默 0 命中，不是报错

| 查询 | 字符数 | 报错 | 命中 |
|---|---:|---|---:|
| `铜` | 1 | 无 | **0** |
| `铜版` | 2 | 无 | **0** |
| `铜版纸` | 3 | 无 | 1 |
| `铜版纸反` | 4 | 无 | 1 |

**静默**是这个坑最危险的地方：`ok: true`、返回空数组，调用方如果只看有没有异常，会把"查不到"误当成"没有相关记忆"。所以代码里 trigram 路对 <3 字符的段显式跳过并标 `reason: 'query_too_short'`，且 trigram 永远不当主路。

### 3.5 召回对比（55 条文档 / 54 个查询）

指标口径：hit@10 = top10 里至少命中一条标注 gold；recall@10 = 命中 gold 数 / 该查询 gold 总数；P@10 = 命中 gold 数 / 实际返回条数；MRR = 第一条 gold 的 1/rank。

| 引擎 | hit@10 | recall@10 | P@10 | MRR | 平均返回条数 |
|---|---:|---:|---:|---:|---:|
| 纯 FTS5 unicode61（原文，默认分词） | 50.0% | 46.9% | 50.0% | 0.500 | 0.5 |
| FTS5 unicode61 + char-space，强制 phrase | 90.7% | 90.7% | 88.7% | 0.889 | 1.3 |
| FTS5 unicode61 + char-space，强制 AND | 90.7% | 90.7% | 88.3% | 0.889 | 1.4 |
| FTS5 unicode61 + char-space，强制 OR | 100.0% | 100.0% | **46.9%** | 0.981 | 4.9 |
| **FTS5 unicode61 + char-space，自适应（≤4 phrase，>4 OR）** | **100.0%** | **100.0%** | **83.6%** | **0.981** | 2.7 |
| FTS5 trigram（原文） | 61.1% | 61.1% | 60.2% | 0.602 | 0.7 |
| 自维护 n-gram 倒排 | 100.0% | 100.0% | 49.9% | 1.000 | 4.6 |
| 参数化 LIKE 全表扫 | 88.9% | 88.9% | 86.9% | 0.889 | 1.3 |
| **RRF 融合（char 自适应 + trigram + ngram 兜底）** | **100.0%** | **100.0%** | **83.6%** | **0.981** | 2.7 |

三条能直接指导实现的结论：

1. **phrase 和 AND 在口语长查询上都会死**（16.7%）：用户说「上次那个铜版纸名片的报价是多少」，里面的「上次/那个/是/多少」不可能同时出现在一条记忆里。
2. **OR 召回满分但精度掉到 46.9%**，不能直接当默认。
3. **自适应（短查询 phrase、长查询 OR）同时拿到 100% 召回和 83.6% 精度**——这是默认配置的由来。

### 3.7 融合权重扫描（默认权重由这张表定，不是拍脑袋）

| 权重方案 | char | trigram | ngram | hit@10 | recall@10 | P@10 | MRR |
|---|---:|---:|---:|---:|---:|---:|---:|
| char_only | 1 | 0 | 0 | 100.0% | 100.0% | 83.6% | 0.981 |
| **char+trigram（采用）** | 1 | 0.6 | 0 | **100.0%** | **100.0%** | **83.6%** | **0.981** |
| char+trigram+ngram 0.2 | 1 | 0.6 | 0.2 | 100.0% | 100.0% | 49.9% | 0.981 |
| char+trigram+ngram 0.4 | 1 | 0.6 | 0.4 | 100.0% | 100.0% | 49.9% | 0.981 |
| char+trigram+ngram 0.6 | 1 | 0.6 | 0.6 | 100.0% | 100.0% | 49.9% | 0.981 |
| char+trigram+ngram 1.0 | 1 | 0.6 | 1 | 100.0% | 100.0% | 49.9% | 0.991 |

**只要 ngram 进排序（哪怕权重 0.2），P@10 就从 83.6% 掉到 49.9%，召回一点没多。** 原因是主路平均只返回 2.7 条，ngram 平均返回 4.6 条，RRF 融合时 ngram 的噪声候选把 top10 的剩余位置填满了。

所以默认权重 `{ char: 1, trigram: 0.6, ngram: 0 }`：ngram 只做两件事——覆盖率诊断、以及主路全空时的兜底。

> P@10 的口径说明：分母是引擎实际返回条数，非 gold 不等于"错误结果"（语料只标了应当命中的文档）。它的用途是横向比较各路噪声水平，不是精确率绝对值。

### 3.8 规模与耗时

合成放大语料（55 条循环扩写，加序号），临时文件库，54 个查询 × 3 轮取均值，已预热：

| 文档数 | 建三套索引 | 每篇耗时 | 库文件 | ngram 行数 | 存储放大 | FTS char | FTS trigram | ngram | LIKE 全扫 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 478 ms | 0.478 ms | 1.99 MB | 33,184 | 33.2× | 0.366 ms | 0.129 ms | 0.784 ms | 0.463 ms |
| 5000 | 3,889 ms | 0.778 ms | 10.15 MB | 173,726 | 34.7× | 0.792 ms | 0.234 ms | 2.946 ms | 0.630 ms |
| 10000 | 9,167 ms | 0.917 ms | 20.30 MB | 349,444 | 34.9× | 1.348 ms | 0.390 ms | 6.213 ms | 1.039 ms |

怎么读这张表：

- **主路够快**：1 万条文档、单次中文查询 1.35 ms。trigram 补充路 0.39 ms。
- **ngram 存储放大 34.9×**（每篇文档约 35 个倒排行）。这是 ngram 只做诊断/兜底、不做主排序的另一个理由——除了精度（§3.7），它还贵。
- **ngram 查询随规模线性变慢**（0.78 → 2.95 → 6.21 ms），因为每次都要取候选后逐文档算覆盖度。做诊断可接受，做排序不可接受。
- **LIKE 全表扫 1.04 ms @ 1 万条**，线性增长。只在兜底路径上用，不进正常查询。
- **建索引 ~0.9 ms/篇**（1 万条 9.2 秒）。历史教训：ngram 表不加 `doc_id` 索引、或每篇都先做一次按 `doc_id` 的 FTS 全表 purge，会退化成 O(n²)——本机测过 1 万条直接跑不完。这两处都已在实现里修掉（§6 第 4 条）。

### 3.9 四种「检索不足」状态（代码判定，不是靠相似度凑）

独立小库、构造明确的场景验证：

| 期望状态 | 实际状态 | 触发查询 | 判定依据 |
|---|---|---|---|
| `no_relevant`（无相关记忆） | ✅ | `量子纠缠退相干` | 三路索引与 LIKE 兜底都没有候选 |
| `insufficient_evidence`（证据不够） | ✅ | `铜版报价脚手架量子纠缠` | 最佳候选覆盖度 0.23 < 阈值 0.34 |
| `source_missing`（来源丢失） | ✅ | `铜版` | 候选在索引里，`source_refs` 无记录 |
| `source_conflict`（来源冲突） | ✅ | `报价` | 同一记忆挂了两条内容指纹不同的来源 |
| `ok`（证据齐全） | ✅ | `哑粉` | 候选齐全、来源完整、覆盖度达标 |

覆盖度 = 命中 n-gram 权重 / 查询总权重（单字 1、双字 2、ASCII 词 2）。这是「可能相关但证据不够」和「有相关记忆」的分界线——**低于阈值就明说不确定，不拿相似结果充数**。

`source_refs` 表不存在时 `sourceBackRefs()` 返回 `available: false`，上层不得当成"来源没问题"。

### 3.10 规范化不变量

`docs/CONTRACTS.md §7` 要求「数字、单位、版本、符号不被不可逆清洗」。实测断言（`tests/search/tokenize.test.mjs`）覆盖 8 个关键样例：`1.2m`、`1200mm`、`2400×600`、`建施-03`、`JS-2026-017`、`readSurface`、`deletion_epoch`、`M100`——经 char-space 规范化后，去掉空白仍与原文逐字符一致。

另外实现了两套文本：**原文（`content`）不动，检索副本（searchable text）做规范化**。规范化只用于检索，不写回原文。

## 4. 架构决策与数据依据

### 4.1 主路用 char-space，不用 unicode61 原文

- 默认 unicode61：中文两字 25%、单字 20%、昵称 0%、长查询 0%（§3.6）。
- char-space：全部类别 100%，P@10 83.6%，MRR 0.981（§3.5）。
- 机制清楚：unicode61 把连续中文当一个 token（`fts5vocab` 直读，§3.2），char-space 把每个汉字变成独立 token 后，两字词变 phrase、单字变 token，都能查。
- 附带的必要修正：**数字↔字母边界也要切**。实测漏检过一次——`1440dpi` 里 `dpi` 切不出来，查 `dpi` 命中率为 0（`q47`）。切开成 `1440 dpi` 后，查 `dpi` 能命中，查 `1440dpi` 仍是相邻 phrase，不丢精确性。

### 4.2 trigram 只当补充，不能当主路

- 可用、且对长中文短语（≥3 字）100% 命中（§3.6 `zh_sentence`）。
- 但**两字/单字静默 0% 命中**（§3.4），中文最常用的两字词、单字全废。
- 融合时给 0.6 权重：召回从 100% 保持，精度不掉（§3.7 第一、二行）。

### 4.3 ngram 不进排序，只做诊断与兜底

- 召回 100%，但 P@10 只有 49.9%（§3.5）。
- 任何非零权重都会把融合精度拉到 49.9%（§3.7）。
- 保留价值：① 算覆盖度，区分「证据不够」；② 排序结果全空时兜底；③ 不依赖 FTS5 的独立实现，可对照。

### 4.4 LIKE 兜底只能查自己的索引副本

实测踩到过：LIKE 兜底原本查 `memories` 原文表，结果「删索引、没删原文」时，**已删记忆还能被 LIKE 捞出来**，删除屏障直接漏（单测 `删除后三套索引都查不到` 抓到）。改成查 `search_fts_trigram.body`（本包的原文副本，随 `removeDoc` 一起清）后闭环。

LIKE 的适用边界也实测清楚：短查询 88.9%，**口语长查询 0%**（§3.6）——它只适合精确子串，所以只做最后兜底，且带 `ESCAPE '\'` 把用户输入的 `%` `_` 当字面量。

### 4.5 查询构造：自适应 phrase/OR

| 查询长度（char-space token 数） | 用的连接方式 | 依据 |
|---|---|---|
| ≤ 4 | phrase（要求相邻） | 短查询要精确，「铜版」不该匹配到「铜…版」分开出现的句子 |
| > 4 | OR（组内括号，段间 AND） | 口语长查询的虚词不能把结果 AND 死；靠 bm25 的 idf 把「的/是/多少」压权 |

所有 token 一律包双引号（§3.3），`OR` 组必须加括号，否则和相邻段的隐式 AND 结合顺序会错。

### 4.6 索引的三套分工与写入成本

- `search_fts_char`（char-space 副本，unicode61）：主路。
- `search_fts_trigram`（原文，trigram）：补充路 + LIKE 兜底的原文副本。
- `search_ngram`（term, doc_id, tf，单字/bigram/ASCII token/3-gram）：诊断与兜底。

**建表语句由 `@dsh-brain/search` 导出、由 `@dsh-brain/memory` 的迁移执行**，检索层自己不建表（CONTRACTS §1）。

## 5. 已知限制与未测项（诚实清单）

**明确的限制（有实测支撑）**

1. 这是**精确字符级检索**的回测。同音字、错别字、繁简混用不在覆盖范围内：`铜板` 不会命中 `铜版`（char 主路命中 0，单测已断言）；库里若只有沾单字的弱相关记忆，会被判成 `insufficient_evidence` 而不是当命中。语义级召回需要 embedding，本报告不涉及。
2. 单字查询会返回较多候选（`char_or` 平均返回 4.9 条），精度靠覆盖度诊断兜，不靠相似度排序。
3. ngram 倒排有存储放大：1 万条文档时 ngram 表 34.9 万行、整库 20.3 MB（§3.8）。
4. 55 条短记忆的语料规模偏小；真实记忆更长、更杂，命中率会低于本报告数字。本报告能证明的是**机制可用**，不是"线上就是 100%"。
5. 含 `"` 的查询靠双写转义，未测极端嵌套引号组合（已测 `"(`, `--`, `x OR y`, `*` 等注入串不抛异常）。

**未测（unknown，不许当成可用）**

1. 繁体中文 / 日文假名 / 韩文：char-space 的 CJK 范围包含假名与谚文，但**没有实测**。
2. 超长文档的分块检索（chunk）：只在单条短记忆上测，没测长文档切块后的边界与页码定位。
3. 并发写入 / 多进程：全部测试是单进程同步，`busy_timeout`、WAL 竞争未压测。
4. `remove_diacritics 2` 与 `1` 的差异：探针文本里没有能区分两者的字符，实测结果相同，差异未测。
5. `unicode61 separators` 的行为：建表通过但 term 无变化，机制未查明，本方案不使用。
6. 数字等价推断（`1.2m` ↔ `1200mm`）：**不做**。按 CONTRACTS §7 保留原始参数，等价推断要另带转换依据，不在检索层做。
7. 大规模（>10 万条）下的性能：只测到 1 万条。

## 6. 给 M2 构包层的坑

1. **用户输入不能直进 `MATCH`。** `建施-03`、`JS-2026-017`、`1.2m`、`build:web` 四种输入会分别抛 `no such column` 和 `syntax error`（§3.3）。必须走 `buildFtsMatch()` 统一转义。
2. **中文必须走 char-space 检索副本，原文另存。** 直接拿 `content` 建 unicode61 索引，中文两字词命中率 25%、单字 20%（§3.6）。两套文本都要存，检索副本可丢、原文不可丢。
3. **trigram 两字以下静默 0 命中**——不报错、不抛异常、就返回空（§3.4）。任何"有结果才算成功"的健康检查都会漏掉这个问题。
4. **ngram 表必须建 `doc_id` 索引。** 不加时按文档查存在性/删除会全表扫；本机 1 万条文档的建索引基准从跑不完降到 9.7 秒（§3.8）。这也是 `WITHOUT ROWID` 表容易忽略的点。
5. **删除屏障要连 LIKE 的源一起管。** LIKE 查外部原文表会漏删（§4.4），默认查本包索引副本。
6. `node --test <目录>` 在本机 Node v24.19.0 上不识别目录参数（把目录当模块 resolve，报 `Cannot find module`）。测试目录放了 `run-all.mjs` 入口绕过；任何地方都不通用，CI 里用 `node --test "tests/search/*.test.mjs"` 更稳。
