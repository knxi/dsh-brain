## 1. 门面契约（已验证，读代码确认）

`packages/persona/src/social.js:1017` `send(candidateId, meta)`：

| 入参 | 含义 |
|---|---|
| `meta.mode` | `'dry_run'`（默认）或 `'approved'`；只有这两种 |
| `meta.channel` | 通道名，默认 `'im'`；本机通道用 `'console'` |

分支行为（逐条对应行号）：

| 条件 | 结果 |
|---|---|
| `!gate.canWrite`（暂停/社交关） | `{sent:false, ok:false, reason:<gate.denied>}`，**不写任何记录**（`:1024`） |
| `mode='dry_run'` | 写一条 `social_sends`（`delivery_mode='dry_run'`，`ok=1`），返回 `reason:'dry_run_only'`，**不调用通道**（`:1028-1039`） |
| `mode='approved'` 且 `!gate.canExternal` | `reason:'external_disabled'`（`:1043`） |
| 候选状态不是 `awaiting_approval`/`scheduled` | `reason:'invalid_status'`（`:1046`）——**刚生成的候选是 `scored`，必须先跟 `arbitrate()`** |
| 没有 `channelHook` | 写 `ok=0` 的发送记录，`reason:'no_channel_configured'`（`:1058`）—— **这就是页面那句「外发能力 无」的来源** |
| 有 hook，hook 返回 `ok:false` | 写 `ok=0` + 错误码，`reason:'channel_rejected'`（`:1080`） |
| 有 hook，成功 | 写 `ok=1`（`delivery_mode='approved'`）+ `external_id`，`reason:'sent'` |

hook 契约：`channelHook({ channel, text, candidate, personId }) => Promise<{ ok: boolean, externalId?, error? }>`，
由 `openBrain({ outboundChannel })` 传入（`packages/memory/src/index.js:205` 透传给 `createSocial`）。

**关键设计（不用改）**：发送失败也一定留一条 `ok=0` 记录——「尝试过但没发出去」不谎称成功。

## 2. 三档方案

### A 档 · 本机 console（**已接，零外发**）

- 实现：`apps/brain-tools/index.js` 里 `consoleChannel` → 追加到 `data/logs/social-outbox.jsonl`，返回 `ok:true`。
- 语义：`send(mode:'approved')` 会写 `social_sends` 成功记录 + 落一行本地 jsonl。**不触达任何第三方账号。**
- 失败：写文件失败 → `ok:false` → 门面记 `ok=0`，页面显示失败原因。
- 停止：`paused=1` 或 `social.enabled=0` 立刻拦住（send 第一步就是 gate）；已有的本地记录可直接删文件。
- 撤回：无外部投递，无撤回问题。
- **风险：几乎为零**。最坏后果是本机多一行日志。

### B 档 · 本机可见通知（**推测，未验证**）

- 想法：候选/发送结果用 DSH 自己的界面通道提示（例如设置页那块「外置大脑」面板、或 Web GUI 的提示条），不经过任何 IM。
- 现状：`apps/brain-tools/client.js` 已有 `settings.section` 注入，可以扩展成「有新候选」的行内提示。
- 需要验证：DSH client 插件是否提供 toast/通知 API——**没查，别当已可用的**。
- 风险：低（仍不出本机）。

### C 档 · 真外发（**推测，需要你点头**）

- 接法：写一个 `channelHook`，把文本交给 QQ/NapCat / `dsh-im` / 邮件之一。
- 已验证存在的相关能力：`dsh_im_return_file`（IM 附件投递）、本机抖音/QQ 相关插件生态。
  **但这些都是「投递文件/附件」，主动社交要的是「发一句话给你本人」——需要一个新的文本发送入口，没有现成 API 可直接用。**
- 接上会发生什么：`send(mode:'approved')` 会真的把候选文本发到你指定的账号。
- 失败：函数式失败会落 `ok=0`；但如果消息已到平台侧再失败（超时/重复），本地记录可能与实际不一致——这是这类通道的固有风险。
- 撤回：**发出去收不回**。只能做到「发之前人审批 + 每日上限 + 静默时段」。
- 风险：高——涉及第三方账号、不可撤回、可能被平台限流/封禁。

---

## 3. 推荐与需要你定的点

**推荐**：现在停在 **A 档**（已接）。它让「批准并发送」这条链路**真的跑得通**（有记录、有回执、有失败原因），
而且不会向任何地方发消息。等你要「真发」时再单独上 C 档。

**需要你点头的只有一点**：C 档要不要接？接哪个通道（QQ / IM / 邮件）？
这个不点头我不会有任何动作——对外发消息是必须你确认的事。

## 4. 附：页面上的「批准」怎么走（已实现的后端链路）

`POST /dsh-brain/api/persona/social/send`（新增，2026-10-31）：
1. `mode:'dry_run'` → 只记试发，不真发；
2. `mode:'approved'` → 若候选是 `scored`，先 `arbitrate()` 过策略闸/预算/静默时段；过了才 `send()` 到 console 通道。
3. 闸门拒了会如实返回 `reason`（静默时段 / 每日上限 / 状态不对），不绕过。

页面按钮由 `persona-page.js` 侧补（两步确认：第一次点只写后果，3 秒不点自动退回）。
